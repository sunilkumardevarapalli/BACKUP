# Java Class Loading & ClassLoader Notes (Simplified)

## 1. Classpath

**Classpath** is the location where the JVM searches for `.class` files and JAR files.

---

# 2. Common Class Loading Errors

| Error                            | Cause                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------- |
| **ClassNotFoundException**       | Class not found in the classpath while loading dynamically (e.g., `Class.forName()`). |
| **NoClassDefFoundError**         | Class was available during compilation but missing at runtime.                        |
| **VerifyError**                  | JVM fails to verify invalid or corrupted bytecode.                                    |
| **UnsupportedClassVersionError** | Class compiled with a newer Java version than the current JVM.                        |
| **ExceptionInInitializerError**  | Exception occurs during static initialization.                                        |

---

# 3. Custom ClassLoader

A **Custom ClassLoader** extends `ClassLoader` and loads classes from sources other than the default classpath.

### Common Sources

* Database
* Network
* Encrypted Files
* Cloud Storage
* Plugin Directories

### Important Methods

* `loadClass()` – Loads a class.
* `findClass()` – Finds class bytecode.
* `defineClass()` – Converts bytecode into a `Class` object.
* `resolveClass()` – Links the class.

---

# 4. defineClass()

`defineClass()` is the core method of `ClassLoader`.

### Flow

```
.class file
      ↓
Read Bytecode
      ↓
defineClass()
      ↓
Class Object
      ↓
resolveClass()
      ↓
Ready to Use
```

### Interview Answer

> `defineClass()` converts raw bytecode into a JVM `Class` object, stores its metadata in Metaspace, verifies the bytecode, and makes the class available for execution.

---

# 5. ClassLoader Memory Leaks

ClassLoader leaks usually happen in enterprise applications during application redeployment.

## Common Causes

* Static variables
* ThreadLocal objects
* Background threads
* JDBC Driver registration
* Cached objects

---

# 6. Preventing ClassLoader Leaks

* Clear static caches
* Remove `ThreadLocal` values
* Stop background threads (`shutdown()`)
* Deregister JDBC drivers
* Close connection pools (`hikariDataSource.close()`)
* Avoid long-lived static references
* Use Dependency Injection instead of global static objects
* Use `WeakReference` where appropriate
* Monitor Metaspace usage

---

# 7. WeakReference

A `WeakReference` allows the JVM to garbage collect an object when no strong references exist.

## Uses

* Memory-sensitive caches
* Listeners
* Metadata caches
* Reduce ClassLoader retention

### Limitation

Always check for `null` because the object may be garbage collected.

### Interview Answer

> `WeakReference` allows the garbage collector to reclaim memory when only weak references remain, making it useful for caches and reducing memory leaks.

---

# 8. JDBC & HikariCP Cleanup

Always close the connection pool during application shutdown.

```
hikariDataSource.close();
```

This releases:

* Database connections
* Worker threads
* Internal caches
* ClassLoader references

---

# 9. Performance Best Practices

* Lazy class loading
* Reuse existing ClassLoaders
* Avoid creating many Custom ClassLoaders
* Minimize dynamic class loading
* Reduce excessive reflection
* Use CDS (Class Data Sharing)
* Avoid heavy static initialization
* Monitor Metaspace
* Prevent ClassLoader leaks

---

# 10. Class Data Sharing (CDS)

## What is CDS?

CDS stores preprocessed class metadata in a shared archive, reducing startup time.

### Benefits

* Faster JVM startup
* Lower memory usage
* Better performance in Docker, Kubernetes, Spring Boot, and Microservices

### Single JVM

* Faster startup

### Multiple JVMs

* Faster startup
* Shared class metadata
* Reduced memory usage

---

# 11. Check if CDS is Enabled

```
java -Xlog:cds -version
```

If you see:

```
Using shared archive
Opened archive
```

CDS is active.

---

# 12. Enable / Disable CDS

### Enable

```
java -Xshare:on MyApplication
```

### Disable

```
java -Xshare:off MyApplication
```

Modern JDKs already enable CDS by default.

---

# 13. Create AppCDS Archive

### Step 1

```
java -XX:DumpLoadedClassList=classes.lst -cp app.jar com.example.Main
```

### Step 2

```
java -Xshare:dump \
-XX:SharedClassListFile=classes.lst \
-XX:SharedArchiveFile=app.jsa \
-cp app.jar
```

### Step 3

```
java -Xshare:on \
-XX:SharedArchiveFile=app.jsa \
-cp app.jar com.example.Main
```

-----------------------------------------------------Great question. These errors occur at **different stages of the class loading process**. Here's exactly **which method** can lead to which error.

| Method                             | What it does                                                          | Possible Errors                                                                   |
| ---------------------------------- | --------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `loadClass()`                      | Searches for the class using parent delegation.                       | `ClassNotFoundException`, `NoClassDefFoundError`, `UnsupportedClassVersionError`  |
| `findClass()`                      | Finds the `.class` file and reads its bytecode.                       | `ClassNotFoundException`, `NoClassDefFoundError`                                  |
| `defineClass()`                    | Converts bytecode into a `Class<?>` object and performs verification. | `VerifyError`, `UnsupportedClassVersionError`, `ClassFormatError`, `LinkageError` |
| `resolveClass()`                   | Performs linking (verification, preparation, resolution).             | `VerifyError`, `NoClassDefFoundError`, `UnsatisfiedLinkError`, `LinkageError`     |
| Static Initialization (`<clinit>`) | Executes static variables and static blocks.                          | `ExceptionInInitializerError`                                                     |

# 1. `loadClass()`

### What happens?

```java
ClassLoader.loadClass("com.demo.Employee");
```

It

1. Checks if the class is already loaded.
2. Delegates to the parent class loader.
3. Calls `findClass()` if the parent cannot find it.

### Error 1: ClassNotFoundException

```java
Class.forName("com.demo.Employee");
```

If

```
Employee.class
```

doesn't exist anywhere in the classpath,

```
java.lang.ClassNotFoundException
```

is thrown.

Example

```
Class.forName("com.demo.Employee");
```

Output

```
Exception in thread "main"
java.lang.ClassNotFoundException: com.demo.Employee
```

---

### Error 2: NoClassDefFoundError

Suppose

```
Employee.class
```

was present during compilation

```
javac Employee.java
```

but later someone deleted

```
Employee.class
```

and then runs

```
java Employee
```

Output

```
NoClassDefFoundError
```

Because JVM expected the class to exist.

---

### Error 3: UnsupportedClassVersionError

Suppose

```
Employee.class
```

was compiled using Java 21.

```
major version = 65
```

Now run it using Java 17.

During loading JVM checks the class version.

Output

```
UnsupportedClassVersionError
```

---

# 2. `findClass()`

This method actually locates

```
Employee.class
```

and reads its bytes.

Example custom class loader

```java
protected Class<?> findClass(String name)
```

If

```
Employee.class
```

is not found,

```
ClassNotFoundException
```

is thrown.

---

# 3. `defineClass()`

This is where JVM converts raw bytes into

```
Class<Employee>
```

Internally

```
byte[]
    ↓
defineClass()
    ↓
Class<?> object
```

---

### Error: VerifyError

Suppose someone modifies the bytecode manually.

Example

Original bytecode

```
push int
return int
```

Modified bytecode

```
push String
return int
```

During verification JVM detects

```
Illegal stack state
```

Output

```
java.lang.VerifyError
```

---

### Error: UnsupportedClassVersionError

Before defining the class JVM checks

```
Major Version
Minor Version
```

If newer than current JVM

```
UnsupportedClassVersionError
```

---

### Error: ClassFormatError

Suppose the

```
Employee.class
```

file is corrupted.

```
CAFEBABE
```

header is missing.

JVM throws

```
ClassFormatError
```

---

# 4. `resolveClass()`

This performs linking.

Internally

```
Verification
Preparation
Resolution
```

---

### VerifyError

Verification happens here.

If bytecode is invalid

```
VerifyError
```

---

### NoClassDefFoundError

Suppose

```
Employee
```

contains

```java
Department dept;
```

During resolution JVM must load

```
Department.class
```

If

```
Department.class
```

is missing

Output

```
NoClassDefFoundError
```

Even though

```
Employee.class
```

was loaded successfully.

---

### LinkageError

Occurs if duplicate or incompatible class definitions are detected.

Example

```java
defineClass("Employee", bytes1);
defineClass("Employee", bytes2);
```

Output

```
LinkageError
```

# 5. Static Initialization (`<clinit>`)

After loading and linking,

JVM initializes static fields and executes static blocks.

Example

```java
class Employee {

    static {
        int x = 10 / 0;
    }
}
```

```java
Class.forName("Employee");
```

Output

```
ExceptionInInitializerError
```

Cause

```
ArithmeticException: / by zero
```

Another example

```java
class Employee {

    static String name = null;

    static {
        System.out.println(name.length());
    }

}
```

Output

```
ExceptionInInitializerError
```

# Complete Flow with Errors

```text
loadClass()
    │
    ├── Search already loaded
    ├── Parent Delegation
    ├── findClass()
    │       │
    │       ├── ClassNotFoundException
    │       └── NoClassDefFoundError (runtime dependency missing)
    │
    ├── defineClass()
    │       │
    │       ├── VerifyError
    │       ├── UnsupportedClassVersionError
    │       ├── ClassFormatError
    │       └── LinkageError
    │
    ├── resolveClass()
    │       │
    │       ├── VerifyError
    │       ├── NoClassDefFoundError
    │       └── LinkageError
    │
    └── Initialization (<clinit>)
            │
            └── ExceptionInInitializerError
```

### Interview Tip

It's helpful to remember **when** these errors occur:

| Stage                                                      | Common Error                           |
| ---------------------------------------------------------- | -------------------------------------- |
| **Finding the class**                                      | `ClassNotFoundException`               |
| **Class available at compile time but missing at runtime** | `NoClassDefFoundError`                 |
| **Defining/verifying bytecode**                            | `VerifyError`, `ClassFormatError`      |
| **Checking class file version**                            | `UnsupportedClassVersionError`         |
| **Resolving referenced classes**                           | `NoClassDefFoundError`, `LinkageError` |
| **Executing static blocks/static field initialization**    | `ExceptionInInitializerError`          |

This mapping is commonly asked in Java and JVM interviews because it connects each error to the exact phase of the JVM class loading lifecycle.
