## One important point

When people say:

> **`java.lang` package**

they mean the **logical package (namespace)**.

When people say:

> **`rt.jar`**

they mean the **physical JAR file on disk**.

So:

* **Logical organization:** `java.lang`, `java.util`, `java.io`, etc.
* **Physical storage (JDK 8):** `rt.jar`

### Simple analogy

Imagine this folder structure:

```text
Library.zip
│
├── English
│      ├── Grammar.pdf
│      ├── Story.pdf
│

* `Library.zip` = `rt.jar`
* `English` = `java.lang`
* `Grammar.pdf` = `String.class`

You wouldn't say **English is outside Library.zip**. It's a folder **inside** the ZIP file.

The same is true for `java.lang` and `rt.jar`.

> **Note:** This explanation applies to **JDK 8 and earlier**. Starting with **Java 9**, `rt.jar` was removed. The same packages (`java.lang`, `java.util`, etc.) still exist logically, but they are stored in **modules** (such as `java.base`) instead of `rt.jar`.

# 🔷 Java 1.8 JVM Changes (Method Area, Heap, Metadata)

## 🔥 1. Biggest Change: PermGen → Metaspace

### 👉 Before Java 8

* **Method Area implemented as PermGen (Permanent Generation)**
* It was part of the **Heap**

### 👉 In Java 8

* **PermGen removed ❌**
* Replaced with **Metaspace ✅**















---

## 🔹 Key Difference

| Feature      | PermGen (Java ≤7)         | Metaspace (Java 8+)          |
| ------------ | ------------------------- | ---------------------------- |
| Location     | Inside Heap               | Outside Heap (Native Memory) |
| Memory limit | Fixed (`-XX:MaxPermSize`) | Dynamic (system memory)      |
| GC issues    | Frequent OOM              | Reduced risk                 |
| Storage      | Class metadata            | Class metadata               |

---

# 🔷 2. Where is Metadata Stored Now?

### 👉 Java 7 and below

* Class metadata stored in **PermGen**

### 👉 Java 8+

* Class metadata stored in **Metaspace (Native Memory)**

---

## 🔹 What Metadata Includes

* Class definitions
* Method information
* Constant pool
* Static variables (partially—see below nuance)

---

👉 Important: Heap still exists, but **cleaned up**

* Objects

* Class metadata (moved to Metaspace)

### ❌ Problems with PermGen

* Auto-resizes
* Better for:

  * Dynamic class loading (Spring, Hibernate, proxies)

# 🔷 Key Point (Short Answer)

> The **Bootstrap ClassLoader is implemented in native code (C/C++)**, but it **reads `.class` bytecode files (or modules) from the JDK and loads them into the JVM memory**, then the JVM interprets/compiles them.

# 🔷 What “written in C++” actually means

* The Bootstrap ClassLoader is part of the **JVM implementation (HotSpot)**
* JVM itself is written in **C/C++**
* So:

  * Class loading logic = C++
  * Class content = Java bytecode (`.class`)

👉 Think of it like:

* C++ code = **loader mechanism**
* `.class` files = **data being loaded**

```

### In Java 8:

```text
<JAVA_HOME>/jre/lib/rt.jar
```

# 🔷 Step-by-Step: How Bootstrap Loads `java.lang.String`

```text
JVM starts
   │
   ▼
Bootstrap ClassLoader (C++ code)
   │
   ▼
Looks into JDK internal storage (modules / rt.jar)
   │
   ▼
Finds java/lang/String.class
   │
   ▼
Reads bytecode into memory
   │
   ▼
Creates Class object in JVM (Metaspace)
   │
   ▼
Class is now available to Java program
```

---

# 🔷 Important Clarification

👉 Bootstrap ClassLoader does **NOT**:

* Write Java code
* Convert `.java` → `.class`

👉 It ONLY:

* Reads `.class` (bytecode)
* Loads into JVM memory

---

# 🔷 Why is it Native (C++)?

### ✅ Reasons:

1. **Performance**

   * JVM startup must be very fast

2. **Security**

   * Core classes must be trusted
   * Cannot be overridden by Java code

3. **Tight OS integration**

   * Memory management
   * Thread handling

---
