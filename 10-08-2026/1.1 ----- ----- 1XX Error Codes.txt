

100 → Continue sending request --> "You may send the request body." 
101 → Switch protocol  --> switch the protocol, commonly HTTP → WebSocket.
102 → Processing --> "I received your request and I'm still processing it."
103 → Early hints  --> Ex: get users list and send to broser before css download and prepare the brosure.


| Code                        | Meaning                                | Typical Purpose                                   |
| --------------------------- | -------------------------------------- | ------------------------------------------------- |
| **100 Continue**            | Client should continue sending request | Large request body / `Expect: 100-continue`       |
| **101 Switching Protocols** | Server agrees to switch protocols      | WebSocket / protocol upgrade                      |
| **102 Processing**          | Server is processing request           | WebDAV; intermediate processing                   |
| **103 Early Hints**         | Provides preliminary headers           | Send preload/resource hints before final response |

103:

The most important rule

A Java return exits the controller method. It does not mean "send an interim HTTP response and then continue."

And:

An HTTP 103 Early Hints response does not cause the client to automatically send the original request again.

              ONE HTTP REQUEST
                     |
                     v
                  SERVER
                     |
              103 Early Hints
                     |
                     v
             Server continues
             processing request
                     |
                     v
                  200 OK
                     |
                     v
                   CLIENT
				   
So 103 → 200 can be two HTTP responses for the same request, but return 103 → return 200 cannot be two normal Java return statements in one controller method.

package com.example.demo.controller;

import com.example.demo.model.User;
import com.example.demo.service.UserService;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

import java.io.IOException;
import java.util.List;

@RestController
@RequestMapping("/api")
public class UserController {

    private final UserService userService;

    public UserController(UserService userService) {
        this.userService = userService;
    }

    @GetMapping("/users")
    public ResponseEntity<List<User>> users(
            HttpServletResponse response) throws IOException {

        // ==========================================
        // STEP 1: Send 103 Early Hints
        // ==========================================

        response.setStatus(103);

        response.setHeader(
                "Link",
                "</css/users.css>; rel=preload; as=style"
        );

        response.setHeader(
                "X-Early-Hint",
                "User list is being prepared"
        );

        response.flushBuffer();


        // ==========================================
        // STEP 2: Continue processing
        // ==========================================

        System.out.println("103 Early Hints sent");

        List<User> users = userService.getUsers();


        // ==========================================
        // STEP 3: Return final response
        // ==========================================

        return ResponseEntity.ok(users);
    }
}

Without the `Link` header:

```text
103 Early Hints
```

has **no useful preload information** for the browser.

With it:

```http
103 Early Hints
Link: </css/users.css>; rel=preload; as=style
```

means:

> **“Browser, start loading this CSS now while the server is preparing the final response.”**

So:

**103 alone → just an early informational response.**
**103 + Link → useful performance optimization.**

# 8. Most important line — `flushBuffer()`

```java
response.flushBuffer();
```

This is the key line in your example.

Normally, the server may keep the response in a buffer.

Conceptually:

```text
setStatus(103)
       ↓
setHeader(...)
       ↓
setHeader(...)
       ↓
Response Buffer
```

Nothing necessarily has been sent to the client yet.

When you call:

```java
response.flushBuffer();
```

you are telling the response:

> **"Flush the buffered response data now."**

Conceptually:

```text
Response Buffer
     |
     | flushBuffer()
     ↓
HTTP connection
     |
     ↓
Client
```

So the intention of this code is:

```text

      +
Link header
      +
X-Early-Hint header
      ↓
Send/flush toward client
```

### Important clarification

`flushBuffer()` does **not mean the Java method ends**.

The controller continues executing.

That's why this works:

The method continues after `flushBuffer()`.

# One Important Real-World Point

There is a subtle issue with this exact implementation.

**Setting `response.setStatus(103)` and calling `flushBuffer()` does not guarantee that every servlet container/proxy/client will actually produce a standards-compliant separate `103 Early Hints` interim response.**

Why?

Because `103 Early Hints` is an **interim HTTP response**, while the normal servlet response API is primarily designed around producing the final response.

So you should verify your:

```text
Spring Boot
    ↓
Servlet container
    ↓
Reverse proxy / API Gateway
    ↓
Load balancer
    ↓
Browser/client
```

all support forwarding 103 correctly.

# The Three Most Important Lines

If you remember only these three:

### 1. `setStatus(103)`

```java
response.setStatus(103);
```

Means:

> **Tell the client this is an Early Hints response.**

### 2. `setHeader()`

```java
response.setHeader("Link", "</css/users.css>; rel=preload; as=style");
```

Means:

> **Tell the client what resource it can start preparing/loading.**

### 3. `flushBuffer()`

```java
response.flushBuffer();
```

Means:

> **Flush the currently buffered response data instead of waiting for the method to finish.**

Then:

```java
userService.getUsers();
```

continues the server-side processing, and:

```java
return ResponseEntity.ok(users);
```

produces the intended **final `200 OK` response**.

### In one sentence

**103 Early Hints = "I'm still working, but you can start preparing these resources now"; 200 OK = "I'm finished, here is the actual result."**

# 7. `101 Switching Protocols`

This one is more interesting for real-time applications.

## Meaning

`101` means:

> **"I agree to switch from the current HTTP protocol to another protocol."**

A common example is **WebSocket**.

---

# 8. HTTP → WebSocket

Normally:

```text
Client
   |
   | HTTP request
   v
Spring Boot
   |
   | HTTP response
   v
Client
```

With WebSocket:

```text
Client
   |
   | HTTP Upgrade Request
   |
   | Upgrade: websocket
   v
Server
   |
   | 101 Switching Protocols
   |
   v
WebSocket Connection
   |
   | <-------------------->
   | Real-time communication
   | <-------------------->
```

The client might send:

```http
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
```

The server responds:

```http
HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
```

After that, communication uses the WebSocket protocol.

---

# 9. Spring Boot WebSocket example

You generally **do not manually return `101` from a REST controller**.

Instead, you configure WebSocket support.

For example:

```java
@Configuration
@EnableWebSocket
public class WebSocketConfig implements WebSocketConfigurer {

    @Override
    public void registerWebSocketHandlers(
            WebSocketHandlerRegistry registry) {

        registry.addHandler(
                new ChatWebSocketHandler(),
                "/chat"
        );
    }
}
```

Handler:

```java
@Component
public class ChatWebSocketHandler
        extends TextWebSocketHandler {

    @Override
    public void handleTextMessage(
            WebSocketSession session,
            TextMessage message)
            throws Exception {

        System.out.println(
                "Message: " + message.getPayload()
        );

        session.sendMessage(
                new TextMessage("Message received")
        );
    }
}
```

The WebSocket infrastructure handles the protocol upgrade.

So don't normally write:

```java
return ResponseEntity
        .status(HttpStatus.SWITCHING_PROTOCOLS)
        .build();
```

for a normal WebSocket implementation.
