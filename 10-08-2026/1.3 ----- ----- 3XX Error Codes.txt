# 300 — Multiple Choices

### Real-time scenario

Suppose your application has multiple representations of a product:

```text
/products/101
```

The server says:

> "There are multiple possible representations. Choose one."

For example:

```text
/products/101?format=json
/products/101?format=xml
/products/101?format=html
```

### Controller

```java
@GetMapping("/products/101")
public ResponseEntity<Void> productChoices() {

    return ResponseEntity
            .status(HttpStatus.MULTIPLE_CHOICES)
            .header("Location", "/products/101?format=json")
            .build();
}
```

Response:

```http
300 Multiple Choices
Location: /products/101?format=json
```

### Flow

```text
Client
   |
   | GET /products/101
   ↓
Server
   |
   | 300 Multiple Choices
   | Multiple representations available
   ↓
Client
   |
   | Selects one representation
   ↓
GET /products/101?format=json
```

### Important

`300` means:

> **"There are multiple possible choices."**

It does **not necessarily mean the browser automatically chooses one**. The client/application may need to choose.

# 303 — See Other

This one is very useful after **POST** requests.

### Real-time scenario

User creates an order:

```http
POST /orders
```

Server creates order `101`.

Instead of returning the entire order page directly, server says:

> "See the order at this other URL."

### Controller

```java
@PostMapping("/orders")
public ResponseEntity<Void> createOrder() {

    // Create order
    int orderId = 101;

    return ResponseEntity
            .status(HttpStatus.SEE_OTHER)
            .location(URI.create("/orders/" + orderId))
            .build();
}
```

Response:

```http
303 See Other
Location: /orders/101
```

Browser then makes:

```http
GET /orders/101
```

### Flow

```text
Client
   |
   | POST /orders
   ↓
Server
   |
   | Create order
   |
   | 303 See Other
   | Location: /orders/101
   ↓
Client
   |
   | GET /orders/101
   ↓
Server
   |
   | 200 OK
   | Order details
   ↓
Client
```

### Why 303?

It is commonly used for:

```text
POST
 ↓
Create something
 ↓
303
 ↓
GET result
```

This is the **Post/Redirect/Get (PRG)** pattern.

# 304 — Not Modified

This one is different.

It is mainly related to **HTTP caching**.

### Scenario

Browser already has:

```text
users.json
```

in its cache.

Browser asks:

> "Has this file changed?"

It sends:

```http
GET /users.json
If-None-Match: "abc123"
```

### Controller

A simplified example:

```java
@GetMapping("/users.json")
public ResponseEntity<Void> users(
        @RequestHeader(value = "If-None-Match", required = false)
        String etag) {

    String currentEtag = "\"abc123\"";

    if (currentEtag.equals(etag)) {

        return ResponseEntity
                .status(HttpStatus.NOT_MODIFIED)
                .build();
    }

    return ResponseEntity
            .ok()
            .eTag(currentEtag)
            .build();
}
```

### Flow

```text
Browser
   |
   | GET /users.json
   | If-None-Match: "abc123"
   ↓
Server
   |
   | Compare ETag
   |
   | Same version
   ↓
   | 304 Not Modified
   ↓
Browser
   |
   | Use cached users.json
```

### Important

The server does **not send the entire response again**.

```text
304
 ↓
Use existing cached response
```

So:

> **304 = "Your cached copy is still valid."**

# 305 — Use Proxy

### Important: Obsolete

Historically, `305` meant:

> **"Use this proxy to access the requested resource."**

Conceptually:

```http
305 Use Proxy
Location: http://proxy.example.com
```

A historical-style Spring example would be:

```java
@GetMapping("/old-proxy")
public ResponseEntity<Void> useProxy() {

    return ResponseEntity
            .status(HttpStatus.USE_PROXY)
            .header("Location", "http://proxy.example.com")
            .build();
}
```

But **do not use 305 in modern application development**.

### Flow — historical concept

```text
Client
   |
   | Request
   ↓
Server
   |
   | 305 Use Proxy
   | Use proxy.example.com
   ↓
Client
   |
   | Request through proxy
   ↓
Proxy
   |
   ↓
Server
```

**Status:** ❌ Obsolete

# 306 — Unused

`306` is **not a status code you should implement**.

Historically it was associated with proxy redirection, but it was later reserved/unused.

So there is no normal real-time REST scenario.

```java
// DON'T implement 306 in a normal REST API
```

Think:

```text
306 = Reserved / Unused
```

# 307 — Temporary Redirect

This is extremely important because it **preserves the HTTP method**.

### Scenario

Suppose your payment API temporarily moved:

```text
/payment
```

to:

```text
/new-payment
```

The original request is:

```http
POST /payment
```

### Controller

```java
@PostMapping("/payment")
public ResponseEntity<Void> payment() {

    return ResponseEntity
            .status(HttpStatus.TEMPORARY_REDIRECT)
            .location(URI.create("/new-payment"))
            .build();
}
```

Response:

```http
307 Temporary Redirect
Location: /new-payment
```

The client should then send:

```http
POST /new-payment
```

### Flow

```text
Client
   |
   | POST /payment
   | payment data
   ↓
Server
   |
   | 307 Temporary Redirect
   | Location: /new-payment
   ↓
Client
   |
   | POST /new-payment
   | SAME payment data
   ↓
Server
   |
   | 200 OK
   ↓
Client
```

### Key point

```text
307 → Temporary
     +
     Preserve HTTP method
```

Yes — **your understanding is correct**, with one small clarification.

When the server returns:

```http
301 Moved Permanently
Location: /users/101
```

it is telling the client:

> **"The resource you requested is now available at `/users/101`."**

### What happens

**1. User initially requests:**

```http
GET /old-user
```

**2. Server responds:**

```http
301 Moved Permanently
Location: /users/101
```

At this point, the server has **not sent the user data**. It has only given the new location.

**3. Browser/client sees `Location` and normally follows the redirect automatically:**

```http
GET /users/101
```

**4. `/users/101` must have a corresponding endpoint**, for example:

```java
@GetMapping("/users/101")
public User getUser() {
    return new User(101, "John");
}
```

or more commonly:

```java
@GetMapping("/users/{id}")
public User getUser(@PathVariable int id) {
    return userService.getUser(id);
}
```

**5. Server finally responds:**

```http
200 OK
```

```json
{
    "id": 101,
    "name": "John"
}
```

### Complete flow

```text
Client
  |
  | GET /old-user
  ↓
Server
  |
  | 301
  | Location: /users/101
  ↓
Client
  |
  | "Okay, I'll go to /users/101"
  |
  | GET /users/101
  ↓
Server
  |
  | Controller for /users/{id}
  ↓
  | 200 OK + User data
  ↓
Client
```

### One important correction

You said:

> "it only intimate use this `/users/101` for next time request."

**Not exactly.** The redirect is primarily telling the client **where to go for the current request**. The client may also remember a `301` redirect and use the new URL for future requests, depending on caching/client behavior.

So:

**301 = "This resource has permanently moved; use this new URL."**

And yes, **the client then makes another request to `/users/101`** to get the actual resource.
