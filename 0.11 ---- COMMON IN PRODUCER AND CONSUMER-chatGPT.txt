# Kafka Producer vs Consumer – Idempotence, Acknowledgement, Duplicate Prevention, Ordering, and Configuration

| Feature                   | **Producer**                                                           | **Consumer**                                                           |
| ------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| **Idempotence**           | Prevents duplicate messages produced due to retries.                   | Prevents processing the same message multiple times.                   |
| **Acknowledgement (ACK)** | Broker confirms message persistence.                                   | Consumer commits offset after successful processing.                   |
| **Avoid Duplicates**      | Producer ID + Sequence Number ensure duplicates are ignored by broker. | Manual offset commit, idempotent business logic, database constraints. |
| **Order Management**      | Maintains order within a partition.                                    | Reads messages in partition order.                                     |
| **Configuration**         | `enable.idempotence`, `acks`, `retries`, etc.                          | `enable.auto.commit`, `max.poll.records`, `isolation.level`, etc.      |

---

# 1. PRODUCER SIDE

## 1. Producer Idempotence

### Purpose

Ensures that **even if the producer retries**, Kafka stores the message **only once**.

### How it Works

Producer sends

```
Message-1
```

Broker crashes before ACK.

Producer retries.

Broker recognizes

* Producer ID (PID)
* Sequence Number

Same sequence number already exists.

Broker ignores duplicate.

Result

```
Topic

Order-101
```

Only one message.

### Configuration

```properties
enable.idempotence=true
```

---

## 2. Producer Acknowledgement (ACK)

Determines **when Kafka considers the write successful.**

### ACK = 0

```
Producer
    |
    |----Message---->
```

Producer never waits.

Fastest.

May lose data.

Configuration

```properties
acks=0
```

---

### ACK = 1

```
Producer
      |
      |------Message-------->
                 Leader
                     |
                 ACK back
```

Leader stores message.

Producer receives ACK.

Follower replication may not happen.

Configuration

```properties
acks=1
```

---

### ACK = all

```
Producer
      |
      |------Message-------->

Leader

↓

Followers replicated

↓

ACK returned
```

Safest.

Configuration

```properties
acks=all
```

---

## 3. Producer Duplicate Prevention

Kafka uses

* Producer ID (PID)
* Sequence Number

Example

```
Retry 1

Order-101
Seq=25

Retry 2

Order-101
Seq=25
```

Broker stores

```
Seq=25
```

Only once.

---

## 4. Producer Order Management

Kafka guarantees ordering

**Inside a partition**

```
Partition-0

Order-1
Order-2
Order-3
Order-4
```

Ordering maintained.

If multiple partitions

```
P0

Order-1
Order-3

P1

Order-2
Order-4
```

Global ordering is not guaranteed.

### To Maintain Order

* Use the same message key.
* Send related events to the same partition.
* Avoid multiple in-flight requests if strict ordering is required.

---

```properties

linger.ms=5

```

# 2. CONSUMER SIDE

## 1. Consumer Idempotence

Kafka **does not provide consumer idempotence automatically.**

Consumer application must ensure processing the same event twice does not produce duplicate effects.

Example

```
Order Created

Offset = 50

Consumer crashes

Restart

Reads Offset = 50 again
```

Application checks

```
Order ID already processed?

Yes

Skip Processing
```

Common techniques:

* Store processed message IDs in a database.
* Use unique database constraints.
* Design business operations to be idempotent (reprocessing has no additional effect).

---

## 2. Consumer Acknowledgement

Consumer acknowledgment means

**Offset Commit**

Offset committed only after successful processing.

### Auto Commit

```
Process

↓

Kafka automatically commits offset
```

Configuration

```properties
enable.auto.commit=true

auto.commit.interval.ms=5000
```

---

### Manual Commit

```
Read

↓

Process

↓

Save DB

↓

commitSync()

↓

Next Message
```

Configuration

```properties
enable.auto.commit=false
```

Program

```java
consumer.commitSync();
```

---

### Async Commit

```
Process

↓

commitAsync()
```

Faster

Possible duplicate processing after failures.

---

## 3. Consumer Duplicate Prevention

Best practices

* Disable auto commit.
* Commit offsets only after successful processing.
* Use idempotent business logic.
* Use unique database constraints.
* Deduplicate using message IDs or event IDs.

Example

```
Message ID

12345
```

Database

```
Already Exists

↓

Skip
```

---

## 4. Consumer Order Management

Kafka guarantees

```
Partition-0

Offset

0

1

2

3

4
```

Consumer reads

```
0

↓

1

↓

2

↓

3

↓

4
```

Ordering preserved.

Ordering may be affected if:

* Multiple threads process messages from the same partition concurrently.
* Offsets are committed before processing completes.

### To Maintain Order

* One consumer thread per partition.
* Process messages sequentially within each partition.
* Commit offsets after processing.

---

# Producer vs Consumer Summary

| Feature                | Producer                                                                                                    | Consumer                                                                                                                                                |
| ---------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Idempotence**        | Built into Kafka (`enable.idempotence=true`) to prevent duplicate writes.                                   | Implemented by the application using idempotent processing and deduplication.                                                                           |
| **Acknowledgement**    | Controlled by `acks=0`, `1`, or `all` to confirm broker persistence.                                        | Controlled by offset commits (`commitSync()`, `commitAsync()`, or auto commit).                                                                         |
| **Avoid Duplicates**   | Producer ID (PID) + Sequence Number eliminate duplicate writes caused by retries.                           | Manual offset commits, unique constraints, and processed-message tracking prevent duplicate processing.                                                 |
| **Order Management**   | Kafka preserves message order within a partition; use the same key to keep related events together.         | Consumers read offsets sequentially within a partition; process sequentially and commit after completion to preserve order.                             |
| **Key Configurations** | `enable.idempotence`, `acks`, `retries`, `max.in.flight.requests.per.connection`, `linger.ms`, `batch.size` | `enable.auto.commit`, `auto.offset.reset`, `max.poll.records`, `session.timeout.ms`, `heartbeat.interval.ms`, `max.poll.interval.ms`, `isolation.level` |

## Interview Answer (30 Seconds)

* **Producer:** Use `enable.idempotence=true` to prevent duplicate writes, choose `acks=all` for maximum durability, use retries safely, and send related messages with the same key to preserve ordering within a partition.
* **Consumer:** Disable auto commit (`enable.auto.commit=false`), process the message successfully before calling `commitSync()`, implement idempotent business logic (such as unique event IDs or database constraints) to avoid duplicate processing, and process each partition sequentially to maintain message order.
