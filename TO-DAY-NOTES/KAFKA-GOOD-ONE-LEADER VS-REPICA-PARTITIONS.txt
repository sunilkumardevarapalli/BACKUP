


This is one of the most common Kafka interview questions. Let's understand **why Kafka does not allow a replication factor greater than the number of brokers.**

---

# Your Configuration

```text
Topic : order-topic
Partitions : 6
Replication Factor : 4
Brokers : 3
```

You have only **3 brokers**:

```text
Broker1
Broker2
Broker3
```

---

# What does Replication Factor = 4 mean?

Replication Factor (RF) means:

> **Each partition must have 4 copies.**

For example, Partition P0 needs:

```text
P0

Leader
Replica1
Replica2
Replica3

Total Copies = 4
```

---

# Where can Kafka store these 4 copies?

You have only 3 brokers.

```text
Broker1
Broker2
Broker3
```

Kafka cannot place two copies of the **same partition** on the same broker.

For example:

```text
Broker1 -> P0 (Leader)

Broker2 -> P0 (Replica)

Broker3 -> P0 (Replica)
```

Only **3 copies** have been placed.

You still need a **4th copy**, but there is no fourth broker.

---

# Can Kafka do this?

```text
Broker1 -> P0 (Leader)

Broker1 -> P0 (Replica)   ❌
```

**No.**

Kafka never stores two copies of the same partition on the same broker.

Why?

Because if Broker1 crashes:

```text
Broker1 ❌ DOWN

Leader P0      ❌ Lost

Replica P0     ❌ Lost
```

Both copies disappear together.

That provides **no fault tolerance**, so Kafka prohibits it.

---

# Visual Diagram

```text
Need 4 copies of P0

                 P0

          +----------------+
          |  Leader Copy   |
          +----------------+
                  |
                  v

Broker1  --->  P0 (Leader)

Broker2  --->  P0 (Replica)

Broker3  --->  P0 (Replica)

????????  --->  P0 (Replica)   ← No Broker Available
```

Kafka cannot find a place for the fourth copy.

---

# That's why Kafka throws an error

```text
Replication factor: 4 larger than available brokers: 3
```

Because:

```text
Required Copies = 4

Available Brokers = 3
```

---

# Valid Configuration

If you add one more broker:

```text
Broker1
Broker2
Broker3
Broker4
```

Now Kafka can place all four copies.

```text
P0

Broker1 -> Leader

Broker2 -> Replica

Broker3 -> Replica

Broker4 -> Replica
```

Now every copy is on a different broker.

---

# Easy Analogy

Imagine you have **3 lockers**.

```text
Locker1
Locker2
Locker3
```

You want to keep **4 backup copies** of the same document.

Rule:

* Only **one copy per locker**.

You can store:

```text
Locker1 -> Copy1

Locker2 -> Copy2

Locker3 -> Copy3
```

Where do you put **Copy4**?

There is no fourth locker.

So it is **impossible** until you add another locker.

# Interview Rule

Always remember:

```text
Number of copies of each partition = Replication Factor
```

and

```text
Each copy must be stored on a different broker.
```

Therefore:

```text
Replication Factor ≤ Number of Brokers
```

### Examples

| Brokers | RF | Valid? | Reason                                      |
| ------: | -: | :----: | ------------------------------------------- |
|       3 |  1 |    ✅   | 1 copy fits on 3 brokers                    |
|       3 |  2 |    ✅   | 2 copies fit on 3 brokers                   |
|       3 |  3 |    ✅   | 3 copies fit on 3 brokers                   |
|       3 |  4 |    ❌   | Needs 4 different brokers, but only 3 exist |
|       4 |  4 |    ✅   | One copy can be placed on each broker       |

This is the reason Kafka rejects **Replication Factor = 4** when there are only **3 brokers**.










------------------------------
The number of possible replica layouts is **very large** because Kafka's partition assigner can distribute replicas in many valid ways while following its rules.

The important rules are:

1. Every partition has **exactly one leader**.
2. The number of copies of a partition = **Replication Factor (RF)**.
3. Two copies of the **same partition** cannot be on the **same broker**.
4. Kafka tries to balance leaders and replicas evenly across brokers.

Below are the most common scenarios.

## Simple Formula (Interview)

If you have:

* **B** = Number of Brokers
* **RF** = Replication Factor

Then:

```text
RF ≤ B
```

and

```text
Number of copies of each partition = RF
```

For example:

* **3 Brokers + RF = 2** → Each partition has **1 Leader + 1 Replica**
* **3 Brokers + RF = 3** → Each partition has **1 Leader + 2 Replicas**
* **4 Brokers + RF = 4** → Each partition has **1 Leader + 3 Replicas**

This is the key relationship between brokers and replicas in Kafka.

# What happens if Broker1 crashes?

Before failure

```
P0 Leader -> Broker1

Replica -> Broker2
```

After failure

```
P0 Leader -> Broker2
```

Now Consumer1 automatically reconnects.

```
Consumer1

      |

Broker2
```

Consumer1 **still owns P0 and P3**.

The only difference is **the leader has moved**, so Consumer1 starts polling from the new leader.

---

## Interview Summary

* **Topic partitions** are distributed across brokers.
* Each partition has **one leader** and **one or more replicas**.
* A **consumer is assigned partitions**, not brokers.
* For each assigned partition, the consumer reads **only from that partition's leader broker**.
* If the leader changes due to a broker failure, the consumer automatically switches to the new leader without changing its partition assignment.
