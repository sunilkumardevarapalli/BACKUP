
# What is Kafka? (Definition)
*****************************

	**Apache Kafka is a distributed event streaming platform used to publish, store, and process large volumes of real-time data (events), fault-tolerantly, and at high speed.**
	

Why kafka what are the benifits:
*******************************

1. **Asynchronous Communication** – Enables producers and consumers to communicate independently without waiting for each other.

2. **High Throughput** – Processes millions of messages/events per second with low latency.

3. **High Scalability** – Scales horizontally by adding more brokers and partitions as traffic grows.

4. **Fault Tolerance** – Ensures continuous operation through replication and automatic leader election when brokers fail.

5. **Reliability** – Stores messages durably on disk and supports acknowledgments (`acks`) to prevent data loss.

6. **Load Balancing** – Distributes data across brokers and partitions among consumers for efficient workload sharing.

7. **Loose Coupling** – Decouples producers and consumers, allowing services to evolve independently.

8. **Event Replay** – Retains events for a configurable period, allowing consumers to reprocess historical data when needed.

## What is Event-Driven Architecture?

**Event-Driven Architecture (EDA)** is a software architecture where services communicate by publishing and consuming **events** instead of making direct synchronous calls.

> **Interview Definition:**
> **Event-Driven Architecture is an architectural pattern where components communicate asynchronously by producing and consuming events through a message broker like Kafka, RabbitMQ, or Pulsar. It enables loose coupling, scalability, fault tolerance, and asynchronous processing.**

-------------------------------------------------------------------------------------------------------------------------

# What is a Broker in Kafka?

A **Kafka Broker** is a **Kafka server** that **stores, manages, and serves messages (events)**.

It receives messages from **producers**, stores them in **topics/partitions**, and delivers them to **consumers**.

> **Interview Definition:**
> **A Kafka Broker is a server in a Kafka cluster responsible for receiving, storing, replicating, and serving messages to consumers.**

---

# What does a Broker do?

A broker performs the following tasks:

1. **Receives messages** from producers.
2. **Stores messages** in topic partitions on disk.
3. **Replicates partitions** to other brokers for fault tolerance.
4. **Serves messages** to consumers.
5. **Participates in leader election** when a broker fails.
6. **Works with other brokers** to form a Kafka cluster.


-------------------------------------------------------------------------------------------------------------------------

# What is a Partition in Kafka?

A **partition** is a **smaller division of a Kafka topic** where messages are stored in the order they are received.


-------------------------------------------------------------------------------------------------------------------------

-------------------------------------------------------------------------------------------------------------------------
HOW PartitionS ARE DEVIDED


1. Key-Based Partitioning (Default)** | Kafka hashes the message key and always sends the same key to the same partition.
 Preserve message ordering for the same entity (e.g., Customer ID, Order ID). 
 
2. Round-Robin (No Key)**             | If no key is provided, Kafka distributes messages evenly across partitions.           | Even load distribution when ordering doesn't matter.  

3. Custom Partitioning**              | You implement your own `Partitioner` to decide which partition receives each message. | Business-specific routing logic.  

4. Manual Partition Assignment**      | The producer explicitly specifies the partition number when sending the message.      | Full control over message placement.        


-------

### Sticky Partitioner (Kafka Producer Optimization)

Since Kafka **2.4**, when **no key** is provided, the default producer uses a **Sticky Partitioner** rather than pure round-robin.

How it works:

```text
Message1 → P1
Message2 → P1
Message3 → P1
(batch sent)

Next batch

Message4 → P2
Message5 → P2
Message6 → P2
```

Instead of changing the partition for every message, Kafka keeps sending messages to the same partition until the current batch is full, then switches to another partition.

# What is a Consumer Group in Kafka?

A **Consumer Group** is a **group of consumers that work together to read messages from a Kafka topic**.

Kafka automatically distributes the topic's partitions among the consumers in the group so that **each partition is consumed by only one consumer within that group**.

> **Interview Definition:**
> **A Consumer Group is a collection of consumers identified by the same `group.id` that cooperate to consume messages from a Kafka topic. Kafka distributes partitions among the consumers to enable parallel processing, load balancing, and fault tolerance.**

---


# Advantages of Consumer Groups

1. **Parallel Processing** – Multiple consumers process messages simultaneously.
2. **Load Balancing** – Kafka distributes partitions among consumers.
3. **Scalability** – Add more consumers to handle more workload (up to the number of partitions).
4. **Fault Tolerance** – If a consumer fails, Kafka reassigns its partitions.
5. **Independent Applications** – Different consumer groups can consume the same topic independently.


-------------------------------------------------------------------------------------------------------------------------

# What is Rebalancing?

**Rebalancing** is the process where Kafka **redistributes partitions among consumers in the same consumer group** whenever the group membership changes.

It ensures:

* Every partition has exactly one consumer.
* Workload is balanced.
* Failed consumers are replaced automatically.

---

# When Does Rebalancing Happen?

Rebalancing occurs when:

1. A new consumer joins the group.
2. A consumer leaves gracefully.
3. A consumer crashes (heartbeat timeout).
4. Number of partitions changes.
5. Consumer restarts.

# What is Consumer Lag in Kafka?

**Consumer Lag** is the **difference between the latest offset in a partition and the last offset processed (or committed) by a consumer.**

> **Interview Definition:**
> **Consumer Lag is the number of messages that have been produced to a Kafka partition but have not yet been consumed by a consumer group.**

---

# Formula

```text
Consumer Lag = Latest Offset − Consumer Committed Offset



# How to Reduce Consumer Lag?

1. **Increase the number of consumers** (up to the number of partitions).
2. **Increase the number of partitions** to allow more parallel consumption.
3. **Optimize message processing** (reduce database/API latency).
4. **Use batch processing** instead of processing one message at a time.
5. **Increase consumer resources** (CPU, memory).
6. **Tune Kafka consumer configurations** such as `max.poll.records`, fetch sizes, etc.



| Solution                     | When to Use                            |
| ---------------------------- | -------------------------------------- |
| Increase Consumers           | Partitions > Consumers                 |
| Increase Partitions          | Need more parallelism                  |
| Optimize Business Logic      | Processing is slow                     |
| Batch Processing             | High message volume                    |
| Scale Consumer Instances     | Need more processing capacity          |
| Use Worker Threads Carefully | CPU-intensive processing               |
| Tune Consumer Configurations | Fetching is inefficient                |
| Reduce Rebalancing           | Frequent consumer joins/leaves         |
| Increase CPU/Memory          | Resource bottlenecks                   |
| Control Producer Rate        | Producer is much faster than consumers |
| Reduce External Calls        | APIs/DBs are slowing processing        |
| Monitor Lag                  | Detect issues early                    |


> **Consumer lag can be reduced by scaling the consumer side and optimizing processing. Common solutions include increasing the number of consumers (up to the number of partitions), increasing topic partitions for more parallelism, optimizing business logic, using batch processing, tuning consumer configurations like `max.poll.records`, reducing unnecessary rebalances with static membership or cooperative sticky assignor, allocating more CPU and memory, minimizing slow external API or database calls, and continuously monitoring lag. The right solution depends on whether the bottleneck is Kafka itself or the consumer application's processing speed.**

## What is Reconciliation?

**Reconciliation** is the process of **comparing data from two or more systems to ensure they match and identifying any differences (mismatches).**

> **Interview Definition:**
> **Reconciliation is the process of verifying that data or transactions across multiple systems are consistent, complete, and accurate by comparing records and resolving any discrepancies.**


A reconciliation process identifies the mismatch and corrects it.

---

# Interview Answer (30 Seconds)

> **Reconciliation is the process of comparing data or transactions between two or more systems to ensure they are consistent and accurate. It identifies missing or mismatched records and helps resolve discrepancies caused by failures such as network issues, crashes, or timeouts. Reconciliation is widely used in banking, payment systems, Kafka-based event-driven architectures, and distributed microservices to maintain data consistency.**

# Why Do We Need Reconciliation?

We need **Reconciliation** because in distributed systems, different systems can become **inconsistent** due to failures such as crashes, network issues, timeouts, or partial processing. Reconciliation detects these inconsistencies and corrects them so that all systems eventually have the same data.

> **Interview Answer:**
> **Reconciliation ensures data consistency by identifying and correcting mismatched or missing records across multiple systems after failures or partial processing.**

---

| **Reason**                                | **One-Line Description**                                                                                             |
| ----------------------------------------- | ---------------------------------------------------------------------------------------
| **1. Network Failures**                   | Ensures consistency when communication between services fails due to network issues or timeouts.                     |
| **2. Application/Consumer Crashes**       | Recovers records that were not fully processed because an application or consumer crashed.                           |
| **3. Database Failures**                  | Identifies and corrects records that failed to be stored or updated in the database.                                 |
| **4. External System Failures**           | Synchronizes data when external systems (e.g., banks or third-party APIs) succeed but local systems are not updated. |
| **5. Message Loss or Partial Processing** | Detects and reprocesses missing or partially processed messages across distributed systems.                          |
| **6. Financial Accuracy**                 | Verifies that transaction amounts and balances match across all financial systems.                                   |
| **7. Compliance and Auditing**            | Maintains accurate records and audit trails to satisfy regulatory and business compliance requirements.              |




# Benefits of Reconciliation

1. Ensures data consistency across systems.
2. Detects missing or duplicate records.
3. Corrects failed or incomplete transactions.
4. Maintains financial accuracy.
5. Supports auditing and regulatory compliance.
6. Increases system reliability in distributed architectures.

---

# Interview Answer (30 Seconds)

> **We need reconciliation because distributed systems can become inconsistent due to network failures, application crashes, database failures, timeouts, or partial processing. Reconciliation compares records across systems, identifies missing or mismatched data, and corrects those discrepancies, ensuring data consistency, financial accuracy, and reliable business operations.**
