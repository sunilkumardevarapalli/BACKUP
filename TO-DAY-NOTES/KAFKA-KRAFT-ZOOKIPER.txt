This is a very important interview topic. Let's understand **both ZooKeeper and KRaft**.

---

# 1. Broker Registration with ZooKeeper (Kafka < 3.x)

Suppose you have three Kafka brokers.

```text
Broker 1 : 9092
Broker 2 : 9093
Broker 3 : 9094
```

One ZooKeeper server is running.

```text
        ZooKeeper
             |
    -------------------
    |        |        |
Broker1   Broker2   Broker3
```

---

## Broker Configuration

Broker1 (`server.properties`)

```properties
broker.id=1
listeners=PLAINTEXT://localhost:9092

zookeeper.connect=localhost:2181
```

Broker2

```properties
broker.id=2
listeners=PLAINTEXT://localhost:9093

zookeeper.connect=localhost:2181
```

Broker3

```properties
broker.id=3
listeners=PLAINTEXT://localhost:9094

zookeeper.connect=localhost:2181
```

Notice

All brokers point to the same ZooKeeper.

---

## What happens when Broker starts?

Suppose Broker1 starts.

```text
Broker1
```

Step 1

Reads configuration

```text
broker.id=1
host=localhost
port=9092
```

Step 2

Connects to ZooKeeper

```text
localhost:2181
```

Step 3

Creates an **ephemeral znode**

```text
/brokers/ids/1
```

Inside it stores

```text
{
 id : 1,
 host : localhost,
 port : 9092
}
```

Broker2

Creates

```text
/brokers/ids/2
```

Broker3

Creates

```text
/brokers/ids/3
```

ZooKeeper now has

```text
ZooKeeper

/brokers

     /ids

        /1

        /2

        /3
```

Kafka now knows there are three brokers.

---

## If Broker2 crashes

Broker2 loses ZooKeeper session.

ZooKeeper automatically deletes

```text
/brokers/ids/2
```

because it is an **ephemeral node**.

Remaining

```text
/brokers

     /1

     /3
```

Kafka immediately knows Broker2 is down.

---

# ZooKeeper also stores

* Broker information
* Topic metadata
* Partition assignments
* Controller election
* ACLs
* Configurations

ZooKeeper was the central metadata store.

---

# 2. Broker Registration in KRaft (Kafka 3.x+)

Kafka removed ZooKeeper.

Instead Kafka itself stores metadata.

There is no external ZooKeeper process.

---

Suppose

```text
Broker1
Broker2
Broker3
```

Configuration

Broker1

```properties
node.id=1

process.roles=broker,controller

controller.quorum.voters=1@localhost:9092,2@localhost:9093,3@localhost:9094
```

Broker2

```properties
node.id=2

process.roles=broker,controller

controller.quorum.voters=1@localhost:9092,2@localhost:9093,3@localhost:9094
```

Broker3

```properties
node.id=3

process.roles=broker,controller

controller.quorum.voters=1@localhost:9092,2@localhost:9093,3@localhost:9094
```

Notice

Every broker knows

```text
Who are the controllers?
```

---

# Startup

Broker1 starts.

Reads

```text
node.id = 1
```

Then connects to controller quorum.

```text
Controller 1

Controller 2

Controller 3
```

One controller becomes Leader.

Suppose

```text
Controller2
```

Leader controller stores metadata.

Broker1 sends

```text
Hi

I'm Broker1

Port 9092

NodeId 1

I'm alive
```

Leader controller writes this into the **metadata log**.

Broker2

Same process.

Broker3

Same process.

Now metadata log contains

```text
Broker1

Broker2

Broker3
```

---

# Metadata Log

Instead of ZooKeeper

Kafka stores

```text
Metadata Log

Broker1

Broker2

Broker3

Topics

Partitions

Leaders

Replicas
```

The controller quorum replicates this metadata log using the Raft consensus algorithm.

---

# If Broker2 crashes

Controller detects

```text
Heartbeat missing
```

Controller updates metadata log.

```text
Broker2

Status

DOWN
```

Leader election begins.

If Broker2 had

```text
Leader

Partition4
```

Controller elects another replica.

```text
Broker3
```

becomes Leader.

---

# ZooKeeper vs KRaft

| ZooKeeper Mode                                       | KRaft Mode                                            |
| ---------------------------------------------------- | ----------------------------------------------------- |
| External ZooKeeper server                            | No ZooKeeper                                          |
| Brokers register under `/brokers/ids`                | Brokers register with the controller quorum           |
| Metadata stored in ZooKeeper znodes                  | Metadata stored in Kafka's metadata log               |
| Controller elected through ZooKeeper                 | Controller elected using the Raft consensus algorithm |
| ZooKeeper detects broker failure via ephemeral nodes | Controller detects broker failure via heartbeats      |
| More components to manage                            | Simpler architecture with fewer moving parts          |

---

# Overall Architecture

### ZooKeeper Mode

```text
                 ZooKeeper
                      |
        -----------------------------
        |             |             |
     Broker1       Broker2       Broker3
```

* Brokers connect to ZooKeeper.
* ZooKeeper tracks broker registration and metadata.

---

### KRaft Mode

```text
          Controller Quorum
        (Raft Metadata Cluster)
                 |
      -------------------------
      |          |           |
   Broker1    Broker2    Broker3
```

* No ZooKeeper.
* Controllers maintain the metadata log.
* Brokers send heartbeats and register directly with the controller quorum.

### Interview answer (30 seconds)

> **In ZooKeeper mode**, each broker starts, connects to ZooKeeper using the `zookeeper.connect` configuration, and creates an ephemeral node under `/brokers/ids/<broker-id>`. ZooKeeper stores broker information and cluster metadata. If a broker crashes, its ephemeral node disappears, allowing Kafka to detect the failure.
>
> **In KRaft mode**, ZooKeeper is removed. Each broker starts with a configured `node.id` and knows the controller quorum through `controller.quorum.voters`. The broker registers with the active controller, which records broker information in Kafka's replicated metadata log. The controller monitors brokers using heartbeats and manages leader elections and metadata changes using the Raft consensus protocol.
